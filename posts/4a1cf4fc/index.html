修复 Shift-Tab 映射失败问题（Fcitx5-Rime / Noctalia 为例）

起因

最近我遇到两个问题：fcitx5-rime 里和 noctalia 的 launcher 按 Shift+Tab 候选不上翻。 这两问题的共同点都在 Shift+Tab 这一个组合键上。我先怀疑是不是两个软件各自有 bug，但又觉得这俩可能是同一个原因。于是从 rime 下手，借助 AI 帮我 Debug。

从 rime 下手排查

先复现现象：

  • 按 Tab：候选下翻正常。
  • 按 Shift+Tab：候选不上翻。如果是在 Kitty 里，那么它会吃掉这个按键，执行对应操作。
  • default.custom.yaml 里 key_binder / selector 都写了 Shift+Tab 的绑定。

排查核心过程的几步：

  1. 跑 wev 然后按 Shift+Tab，可以看到输出的 keysym 是 ISO_Left_Tab(65056)，修饰位 Shift。
  2. fcitx5 的 key_trace 日志显示 Key(Shift+Tab)。（一开始我也被这个骗了，但实际上这是 Key::toString() 的显示层归一化——不等于传下去的就是 Tab。）
  3. Rime receive key 日志打印 Shift+ISO_Left_Tab，说明按键确实进了 librime，只是没匹配上。
  4. 读源码确认传参。 fcitx5-rime 的 src/rimestate.cpp 里 keyEvent() 用的是 event.rawKey().sym()，未归一化，所以交给 librime 的是 { sym=65056 (ISO_Left_Tab), modifier=Shift }。
  5. 确认 librime 的匹配语义。 KeyBindingProcessor::ProcessKeyEvent 用 std::map<KeyEvent>::find() 做精确 (keycode, modifier) 匹配，不把 ISO_Left_Tab 当 Tab 归一化。

后面几步（读 librime 源码、确认匹配语义）是借助 AI 完成的。

根因

配置项 解析结果 (keycode, modifier) 与 (65056, Shift) 比较
Shift+Tab (65289, Shift) 不同 keycode
ISO_Left_Tab (65056, 无修饰) 修饰不匹配
Shift+ISO_Left_Tab (65056, Shift) 精确相等

Tab 正常是因为它的事件 (65289, 0) 和配置里的 Tab 解析结果完全一致；而 Shift+Tab 失败，是因为 rime-prelude 的惯用配置只覆盖了 Shift+Tab(65289, Shift) 与 ISO_Left_Tab(65056, 无修饰) 两条，唯独漏掉了表格里第三种形态 Shift+ISO_Left_Tab(65056, Shift)，恰好就是实际事件。

简单解释 ISO_Left_Tab

Tab 键对应的标准 keysym 是 XK_Tab (0xFF09 / 65289)。当按下 Shift+Tab 时，在 XKB/libxkbcommon 层通常会生成一个特殊 keysym：ISO_Left_Tab (0xFE20 / 65056)，同时保留 Shift 修饰位。ISO_Left_Tab 表示反向 Tab（backtab），属于 X11 keysym 中 ISO 系列符号。

Wayland 的 wl_keyboard 协议本身不负责 keysym 转换，而是由 compositor 通常通过 libxkbcommon 根据 XKB keymap 将物理按键转换为 keysym。某些程序如果直接用 keysym + modifier 精确匹配，而没有将 ISO_Left_Tab 归一化为 Tab，就会导致配置中的 Shift+Tab 无法匹配，此时需要显式绑定 Shift+ISO_Left_Tab。
